# TRG Prime 3.685.2

7 November 2026. Three small fixes Graham approved after 3.685.1: two Creature Codex entries whose ids Foundry could not load, a schema snapshot that named the wrong Foundry build, and a combat's end being cleared twice when two GMs are connected. Built on 3.685.1.

- **Install over 3.685.1.** No migration, and no world data changes. Nothing rewrites an owned or world item at load.
- **Modules:** Eldritch Arts 0.10.1 (needs 3.685.1 or later) and Inner Tempest (needs 3.674.2 or later) run on it unchanged. No module pin changes.

## For every world

**Scorching Breath and Wing Buffet open from the compendium** (found live on Foundry 14.367: both loaded with a null document id, and the Creature Abilities index listed a third, null-id Scorching Breath)
- **Before:** the two Fiends & Fables 3.0 entries authored at 3.631.0 had 17-character ids, "ff30ScorchingBrth" and "ff30WingBuffet001". A Foundry id is exactly 16 letters and digits. Foundry read both back with no id, so the index showed them but they could not be opened or found by id. They were the only invalid ids among the core packs' 2,613 documents, and nothing referred to them by id.
- **Now:** they are **"ff30ScorchBreath"** and **"ff30WingBuffet01"**, each used once across the core packs. The Creature Abilities pack was rebuilt by the project's own tool (`declare-ff30-codex.mjs`). It now deletes the two retired keys, writes the entries again under the new ids with the same content, and compacts the pack so the old records are gone from its files as well as from its index. The pack still holds 105 entries.
- **A copy already dragged from the compendium onto an actor** has its own id and is unaffected. It keeps working as before.

**The schema snapshot names the build it was checked on**
- **Before:** `FOUNDRY_SCHEMA_SNAPSHOT.foundry` in `module/foundry-schemas.mjs` read "14.363". The live world runs Foundry 14.367, so the "Verify Foundry Integration" macro's S4 ("the snapshot was recorded on this build") reported a mismatch.
- **Now:** "14.367". The live comparison on 14.367 (`snapshotDrift` of `coreSchemasOnly(captureSchemas(CONFIG.RegionBehavior.dataModels))`) found no drift (gone [], grew []), so the twelve recorded field lists are 3.685.1's, unchanged. `system.json`'s `compatibility.verified` was already 14.367. The dated notes in `effect-change-types.mjs` and `deletion.mjs` describe what was seen on 14.363 and are left as they are.

**A combat's end is cleared once with two GMs connected**
- **Before:** the `deleteCombat` hook in `module/combat/turn-records.mjs`, which clears each combatant's attack count, per-turn trait record and opening Flat-Footed, checked `game.user.isGM`. The hook fires on every client, so with two GMs connected (Graham's world has "Gamemaster" and "Claude") both cleared, and both deleted the same Flat-Footed effects. The second delete failed with "does not exist" in that GM's console.
- **Now:** it checks `isActingGM()` (`module/acting-gm.mjs`), like the ammunition-recovery `deleteCombat` hook already did. Only the active GM clears. A lone GM with no active GM designated still clears, through `isActingGM`'s fallback.
- **The other combat hooks were checked again.** Every other `updateCombat` / `deleteCombat` hook, and `TRGCombat`'s `_onStartTurn` / `_onEndTurn`, already use `isActingGM` (directly or through `TRGCombat.automates`). There is no `deleteCombatant` hook. This was the only combat hook with the broad guard.

## Harnesses

- **`verify-pack-ids` (new, 18 checks):** reads **every built pack**: the 31 that `system.json` declares, plus the 12 undeclared directories under `packs/`. It fails on any document `_id` that is not 16 alphanumeric characters, whether it is a top-level `_id`, an id in an embedded record's key chain (`!items.effects!<parent>.<id>`), an id in a parent's `effects` / `items` list, or an inline embedded document. It also fails on a key whose id is not the record's `_id`. The rule lives in `tools/lib/pack-ids.mjs` and is driven on hand-built records first (A1–A8). The packs come next (B1–B7): each declared pack opens and holds records; no bad id appears in any of the 2,613 records; the two retired ids are gone; the new ids are present under the same names and used once each. Last are the sources (C1–C2). It reads each pack from a **temporary copy**, so running it does not dirty `packs/`.
- **`mutate-pack-ids` (new):** 18 mutations, all caught. 12 change the source: the rule's id shape, each of its four id checks and the key depth, the declarations' two ids, and the declare tool's delete and compaction. 6 change the data: each copies `packs/` to a temporary directory, adds one bad record, and points the verify at the copy through `TRG_PACK_IDS_ROOT`. The six records are the old Scorching Breath key, a missing Wing Buffet, an embedded effect with a 17-character id, a parent listing a bad id, a null id in an undeclared directory, and a declared pack removed. None of them writes to `packs/`.
- **`verify-fixes-3685-2` (new, 12 checks):** drives the real `deleteCombat` hook on **two GM clients with one active GM**, running together as Foundry runs them, where each write lands a moment later and a second delete of the same effect throws as the world does. The Flat-Footed is deleted once (G1); the attack count and trait record are cleared once with no error (G2); the GM who is not active, and a player, change nothing (G3, G4); a lone GM with no active GM still clears and a player does not (G5, G6); the guard and import are read (G7). The old `isGM` guard fails G1–G4 and G7: two deletes, four unsets, and "ActiveEffect … does not exist". It also checks the snapshot's build against `compatibility.verified` (S1), pins the field lists' digest (S2), and checks the version and download (Z1, Z2).
- **`mutate-fixes-3685-2` (new):** 9 mutations, all caught: the old `isGM` guard, no guard, `isActingGM` not comparing the active GM with this client, its lone-GM fallback, the Flat-Footed not cleared, the stale build, a dropped recorded field, and the version and download.
- **`verify-ff30-codex`:** a new C3b pins the two sixteen-character ids and checks that the old keys are absent from the built pack (81 checks, from 80). `mutate-ff30-codex` gains the matching mutation (58, from 57, all caught).
- **`mutate-drive-3622`:** "every client clears" is re-anchored on the new `if (!isActingGM()) return;` line. `verify-drive-3622` E1–E2 and `verify-drive-36221` C1 drive the hook with no active GM designated, so they take `isActingGM`'s `isGM` fallback and pass unchanged.
- **Re-anchored:** the version anchors of 19 mutate files point at 3.685.2, as does `mutate-release-links`' download anchor. `mutate-fixes-3685-2` adds a twentieth version anchor.
- **Run:** every `verify-*` passes in the main tree (357: 355 and the two new ones). Afterwards the packs were restored (`git checkout -- packs && git clean -fdq packs`), and then Creature Abilities was rebuilt with `declare-ff30-codex.mjs`, the only pack this release changes. `abilities` and `feats` were restored again after the tool opened them. The rebuilt pack holds 105 entries, and a byte scan of its files finds neither old id. Every mutate file whose anchors touch a changed file was run in a scratch copy: 29 files and 1,224 mutations (`turn-records`, `acting-gm`, `foundry-schemas`, `system.json`, the codex declarations and declare tool), all caught.
- **`verify-rules-have-callers`:** no new uncalled export and no new keep. The new exports are in `tools/lib/`, outside the ratchet's roots.

## For Graham

- **`tools/foundry-globals.json` still says `"foundryVersion": "14.363"`, and this release leaves it.** It records a different fact from the schema snapshot: the build on which the 23 host globals `verify-no-undefined-names` accepts were confirmed in a live client (`foundryBuild` 363, `capturedAt` 2026-10-09). The only thing that reads `foundryVersion` is that verify's summary line. Nothing here can confirm the list against 14.367 without a live client. To re-record it, run `node tools/generate-foundry-globals.mjs --generation 14 --build 367 --add <name>` after checking in the world, or use the browser snippet in that file's header.
- **The broad `isGM` guard remains on some hooks outside combat** that change the world. This release does not change them; Graham approved only the combat fix. Found in review:
  - `magic/conjured-item-workflow.mjs`'s `deleteItem` hook deletes the conjured item's clock effects. Two GMs both delete; the second error is swallowed by `.catch(() => {})`, so this is harmless.
  - `magic/power-crystal-workflow.mjs`'s `createItem` and `deleteItem` hooks settle Power Crystals against the PP pool. With two GMs, a timing race could add or take a crystal's points twice (up to the maximum).
  - `magic/power-crystal-workflow.mjs`'s `preUpdateActor` hook is **not** a duplicate: Foundry runs `preUpdate*` only on the client that made the update, so moving it to the acting GM would be wrong. It points to a different, unconfirmed question for a live check: a PP spend made on a player's own client runs the hook only there, where `isGM` is false, so crystals may not draw down for player spends.
  - `magic/pending-cast-workflow.mjs`'s `ready` hook clears a lapsed cast. Two GMs who load together can each post a "— Lapsed" card. More seriously, any GM who loads or reloads mid-session lapses every pending cast, including one a player is still making in their own browser; the acting-GM guard alone would not fix that.
  - `peril-workflow.mjs`'s `updateWorldTime` hook re-arms suppressed perils. Both GMs re-arm, and each posts a whispered "armed again" card.
- **Inner Tempest dragons gain two specials they were missing.** Inner Tempest finds dragon specials in this compendium by name and then loads them by id. While the ids were invalid it loaded nothing, so dragons never received Wing Buffet (level 10+) or Scorching Breath (level 20+). From 3.685.2 they should arrive on the dragon's next reconcile. Inner Tempest's code is unchanged; its behaviour in a live world changes.

  Each is a one-line change to `isActingGM()` if Graham wants them.
- **The index's third, null-id Scorching Breath** was not in the pack: the built pack held exactly two invalid records. It is most likely the world's cached index entry for the old record. It should be gone once the system is reinstalled and the world reloaded. Worth a look in the live test.
