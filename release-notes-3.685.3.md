# TRG Prime 3.685.3

8 November 2026. The five hooks the 3.685.2 review listed under "For Graham", fixed: each asked `game.user.isGM` and so ran on the wrong clients. Then the older defects a second, independent review of this release found, folded in at the same version: Power Crystal settlements racing each other, a crystal's departure draining the others, three hooks with no client guard at all, and a player's casting the GM's client could not reach. Graham: "Fix the problems first". Built on 3.685.2. No game rule changes; these change only which client does the work, and when.

- **Install over 3.685.2.** No migration, and no world data changes. Nothing rewrites an owned or world item at load.
- **Modules:** Eldritch Arts 0.10.1 (needs 3.685.1 or later) and Inner Tempest (needs 3.674.2 or later) run on it unchanged. No module pin changes, and neither module needed a change.

## For every world

**A Power Crystal is drawn down when a player spends from it** (the most visible change)
- **Before:** the draw-down runs in a `preUpdateActor` hook in `magic/power-crystal-workflow.mjs`, and it asked `game.user.isGM`. Foundry runs `preUpdate*` hooks only on the client that makes the update. A player's cast from their own sheet runs `castSpell` on the player's client, and its `actor.update` of the pool fires the hook there and nowhere else. On that client `isGM` is false, so the hook returned. Nothing else settles crystals: no GM-side `updateActor` hook reads them, and no relay carries a player's PP spend to the GM. So a player holding a crystal spent their pool down, but the crystal kept its points and the derived maximum kept counting it. Only a spend the GM made, or one a GM relay wrote, drew a crystal down.
- **Now:** the hook asks `actor.isOwner`. It still runs on exactly one client: the one that made the update. The guard is not there to remove duplicates. It states the permission the settlement needs, because every write it makes is to that actor's own embedded items: a part-spent crystal's flag, the emptied crystal's flag set to 0, the emptied crystal's deletion, and a chat card. An owner may make all of those. No other actor is written, so no relay or extra permission is needed. A GM owns every actor, so a GM's spend, or a relay the GM writes for a player, settles exactly as before. No GM settles twice, because no GM's client runs the hook for a player's update.
- **What a player will see:** the crystal now shrinks, and dissolves with its card, when the player casts from it. Before, it did so only when the GM spent.

**A Power Crystal's arrival and departure are settled once with two GMs connected**
- **Before:** the `createItem` and `deleteItem` hooks in the same file asked `game.user.isGM`. Both fire on every client, so with two GMs connected both settled the pool. If one GM's write landed before the other read the pool, a crystal's points were added twice (capped at the maximum) or taken twice. Driven: 5 + 3 became 11, not 8, and 13 − 3 became 7, not 10.
- **Now:** both ask `isActingGM()` (`module/acting-gm.mjs`). Neither reads the creating or deleting user, nor any option passed to the create, so nothing in them depended on running on the client that made the change. A lone GM with no active GM designated still settles, through `isActingGM`'s fallback.

**A conjured item's clock is deleted once**
- **Before:** `magic/conjured-item-workflow.mjs`'s `deleteItem` hook, which removes a conjured item's companion clock effect, asked `game.user.isGM`. Both GMs deleted the clock, and the second delete's "does not exist" was swallowed by its `.catch`.
- **Now:** `isActingGM()`.

**A suppressed peril is re-armed once**
- **Before:** `peril-workflow.mjs`'s `updateWorldTime` hook asked `game.user.isGM`. Both GMs re-armed each peril whose suppression had run out, and each whispered its own "armed again" card.
- **Now:** `isActingGM()`. The `isGM` check inside `rearmSuppressedPerils` stays; it can no longer change an answer.

**A casting in progress lapses only when nobody is still making it**
- **Before:** `magic/pending-cast-workflow.mjs`'s `ready` hook, on any GM's load, cleared every actor's pending-cast flag and posted "— Lapsed". Two GMs loading together could each post the card. Worse, a GM who loaded or reloaded mid-session lapsed a casting a player was still making in their own open browser. That player's Complete button still resolved the cast, so a spell landed after its card had called it lapsed.
- **Now:** a new pending-cast record carries **`userId`**, the user whose browser holds the cast's promise. Nothing else reads it: the record's other readers (the turn payment, the card buttons, `game.trgPrime.pendingCast.status`, the interrupt) read only its existing fields. At startup each flag is asked of the new pure rule `pendingCastLapsesAtStartup` (`magic/pending-cast.mjs`):
  - **Your own casting:** the record names this client's user, so its promise went with the reload. This client lapses it, whether it belongs to a GM or a player, and it owns the caster because it cast with it.
  - **Someone else's casting:** only the acting GM lapses it, and only if that user is no longer connected.
  - **A record that names nobody** (written before 3.685.3): the acting GM lapses it only if no player who owns the caster is connected. This is the conservative choice. If such a player is connected, the cast may be theirs, and leaving the flag costs nothing, because a turn charges no AP toward a flag with no promise behind it. A GM's own NPC has no such player, so its casting lapses as it always did. No age threshold was used. The record's `startedAt` is world time, which a GM can move at will, and nothing in the code already lapses a casting by age.
- **The card says why:** "when the world reloaded" for your own casting or a record that names nobody, and "by someone who is no longer connected" otherwise.

**Power Crystal settlements on one creature run one at a time** (review finding 1)
- **Before:** a cast and its surcharge write the pool twice in a row (`cast-workflow.mjs`'s `casterPPSpent`, then `surcharge.pp`). Each write queued a settlement, and each read the crystal's points from the local item. A flag write does not reach the local item until the server answers, so the second settlement read the points the first had not yet written and wrote its answer over the first. A 3 PP crystal spent 2 and then 1 was left holding 2, not dissolved (the reviewer's probe, reproduced by R1).
- **Now:** each settlement on a client waits for the last one on the same creature to finish, every write awaited (`inTurn` in `power-crystal-workflow.mjs`). Foundry's update promise resolves once the local document has the change, so the next settlement reads what the last one wrote. An emptied crystal is deleted once, and one card is posted for each spend that empties one. Arrivals and departures queue on the same line.

**A crystal leaving takes only its own points** (review finding 4)
- **Before:** `settleCrystalDeparture` takes a leaving crystal's points out of the pool with an ordinary update, and the spend hook read that fall as a spend against the crystals still held. Own maximum 10, crystals of 3 and 2, pool 15: the 3 expired, the pool went to 12, and the 2 was drawn down and dissolved too, leaving 12 over a maximum of 10.
- **Now:** the departure's write carries the update option `trgCrystalDeparture`, and the spend hook passes it by. The arithmetic is the one the code already had (`crystalDeparture`: the pool less the leaving crystal's points): 15 − 3 = 12, under the new maximum of 12, with the 2 intact. Below the maximum it is the same: 12 − 3 = 9, under 12. A pool that sat at or under the old maximum is always at or under the new one after this, so no clamp was added. An unmarked fall is still a spend.

**Going under water, an affliction's cure and a temporary conviction point are each written once** (review findings 2 and 5)
- **Before:** `combat/underwater-workflow.mjs`'s `updateToken`, `combat/affliction-workflow.mjs`'s `deleteItem` and `magic/bardic-conviction.mjs`'s `deleteActiveEffect` had no client guard. Each fires on every client, so every client that owned the creature did the work, and a client that did not was refused. Entering water gave two Submerged effects, two cards and two breaths held; leaving took off only one, so the acid and fire resistance stayed. An affliction's conditions were withdrawn by each owner, the losers told the effect did not exist. A temporary conviction point was reclaimed by each.
- **Now:** each asks `isActingClientFor(actor)` (new in `acting-gm.mjs`): the acting GM, or, with no GM connected, exactly one connected owner, the one with the lowest user id, so every client reaches the same answer without asking. (The second review: `isActingGM()` alone is false on every client when no GM is connected, so a player's lone session got no Submerged at all, a cured affliction kept its conditions, and a temporary point was never reclaimed — 3.685.2 did all three, in duplicate. The core had no "one owner client" helper to reuse.) None of them asks the moving or deleting user anything: they write an effect, a status, the drowning flag, a condition, the conviction pool and a card, all of which the acting GM may write. The affliction's withdrawal raises its `releasing` flag on the client that runs it, which is the same client whose deletes the condition lock then sees, so the lock still lets the cure through.
- **Water is read on the acting GM's client.** It asks the Region's own token set first, which Foundry keeps on every client, and the token's placeable only as a fallback. A GM viewing another scene has no placeable for the token; whether the Region's token set is always current there is worth a live check (below).

**A player's casting is reached from the GM's client** (review findings 3 and 6)
- **Before:** a casting with extra time is held by a promise in the caster's browser. Three things looked for it on another client and found nothing:
  - Phase 1 of a turn runs on a GM's client and called `payPendingCastTurn`, which answers null without the promise. So a player's extra-AP window was never paid down, and no turn card carried their Complete button.
  - The hit-point interrupt runs on the client that makes the hit-point update, and the critical-injury interrupt on the client that rolls it: the GM's, for an NPC's blow. Both asked `waiting`, so damage the GM applied never interrupted a player's casting.
  - `game.trgPrime.pendingCast.stop` on the GM's client cleared the flag, answered false and posted nothing.
- **Now:** each is asked of the client that holds the casting, over the system's socket, using the same ask-and-answer the reaction ask (`reactions/reaction-ask-workflow.mjs`) already uses: the `system.trg-prime` channel, a request id, the user it is for, a wait, and a user who leaves answering at once. The actions are `pendingCast.ask` and `pendingCast.answer`; nothing else uses that prefix.
  - **Who holds it:** the record's `userId` when that user is connected (`pendingCastHolder` in `magic/pending-cast.mjs`). A record from before 3.685.3 names nobody, so its first connected player owner is asked.
  - **What runs there** is the same function the caster's own client always ran (`payHere`, `interruptHere`, `stopHere`), so the rules for paying and interrupting are unchanged. The payment's AP is spent on the holder's client, as a player's own spends are, and the line and buttons come back for the GM's Phase 1 card. The blow's source, which the damage path notes in memory on the striking client, is sent with the interrupt so a module's step (Magical Retribution) still sees it.
  - **A Complete pressed on another client** is relayed the same way, so the GM's Phase 1 card's Complete button works for the player too. The holder completes it only once the time is paid (`pendingCastReady`), as the card offers the button only then.
  - **Who may ask** (the second review, and Graham's ruling on it): the holder checks the asker per operation. An **interruption** is what damage does under the rules, not a control, so it is honoured from any connected user: a player's critical injury on another player's casting caster interrupts it at the fumble degree, as the same blow would on the caster's own client. A **payment** is Phase 1's, so only a GM may ask for one. **Stop** and **Complete** are the caster's choices: a GM or an owner of the caster only, and the card's buttons do nothing, with a notice, for anybody else. Before this a player could stop or complete another player's casting from the chat log. These checks guard against mis-clicks and stale or buggy clients; they are not a security boundary (see "For Graham").
  - **Who may answer** (the second review): every acknowledgement and answer carries the answerer's user id, and the asker takes it only from the holder it asked. The reaction ask (`reactions/reaction-ask-workflow.mjs`) trusted any answer with the right request id in the same way; it now carries and checks the answerer's id too (`mutate-ea-block3b-core` re-anchored to it).
  - **The GM's stop** reaches the holder, who stops the casting and posts the "Stopped" card. Only when nobody holds it does the asking client clear the flag itself, and only if that write succeeds (a GM or an owner); then it posts the card and answers true. A holder who is connected but does not answer, refuses, or leaves mid-ask stops nothing: the flag stays, no card is posted, and the asker is told (the second review: a timed-out stop used to clear the flag and post "Stopped" over a casting its player could still complete). A Stop on a flag with no promise behind it (after a reload) now also posts the card rather than doing nothing. A Complete follows the same rule.
  - **The wait, as the reaction ask waits** (the second review): the asker's screen says "Waiting for <player>…"; the holder acknowledges at once (`pendingCast.accepted`); the asker waits 10 seconds for that and, once acknowledged, up to five minutes while the holder works, so a module's step (Magical Retribution's dialog and roll) is waited for rather than rolled past. Only a holder that never acknowledges, or leaves, falls back to the behaviour before 3.685.3: no payment, no interruption, Phase 1 going on without the line. A holder who disconnects mid-ask answers at once.
  - **The payment counts only what was spent** (the second review). `spendActionPoints` reads the spending client's own `game.combat` and cannot be told another, and it spends nothing when the actor is not in that combat; the window was credited regardless. Now the ask names the GM's combat: a holder viewing a different combat pays nothing and the Phase 1 line says why ("the caster's player is viewing a different combat"), and only AP the spender's receipt says left the pool is counted.
  - **A payment and a blow together** (the second review): a payment still being spent when an interruption settles the window no longer writes the record back afterwards and so cannot bring the flag back as a ghost.

## For Graham

- **The casting relay trusts its own messages.** Foundry's socket does not tell the receiver who sent a message, so the asker's `userId` and the answerer's `answererId` are taken from the message itself. The per-operation checks and the answer-from-the-holder check stop mis-clicks, stray answers and stale or buggy clients. They do not stop a player who edits socket messages in the browser console: such a player could pose as the GM to pay, stop or complete another player's casting, or answer for the holder. The reaction ask has always had the same limit. Closing it would need the server to vouch for the sender (for example, routing every write through a GM). For a table of trusted players this is acceptable, and it is strictly tighter than 3.685.2, which checked nothing.
- **An interruption can be asked by anyone** (by the rules, damage interrupts whoever deals it). So a tampering client could interrupt a casting without dealing damage, or name a different source for Magical Retribution's offer; the caster's player still sees and decides that offer. 3.685.2 allowed this too.
- **Phase 1 pays against the combat the GM's tracker is showing**, not necessarily the combat whose turn started. With two combats running and the GM viewing the other one, the payment is refused and nothing is spent or credited; it fails safe. Rare; not changed in this release.

Nothing here needs a ruling; all of it is for a live check or a later release.

- **Worth one live drive with a player at the table:** a player casting with extra AP in combat while the GM runs the turns (Phase 1 pays it down and the Complete button arrives), the GM hitting that caster (the casting is interrupted on the player's screen), and the GM's `game.trgPrime.pendingCast.stop`. The relay is driven here with simulated clients, not yet in Foundry.
- **Water on a scene the GM is not viewing.** The acting GM now settles water. It reads the Region's own token set, which Foundry keeps on every client, so it should be right; but if the GM is on another scene and that set lags, nobody would settle it until the GM looks. Worth one check: move a player's token into water while the GM views a different scene.
- **A player who disconnects mid-cast while the GM stays:** no `userConnected` lapse was added. Lapsing on disconnect would also lapse a casting whose browser only lost its socket for a moment, because the promise survives a reconnect, and post a wrong "— Lapsed" card. The flag lingers harmlessly until the next GM load, which lapses it once that user is gone; the GM's stop now ends it at once, with the card.
- **Timing windows left as they are** (minor; each needs two things to happen within a moment of each other):
  - Two GMs loading together, while the active-GM choice is still settling, could each see themselves as acting and each lapse a disconnected player's casting (one card each).
  - A user reloading at the same moment as the acting GM loads could be counted as disconnected by the GM and also lapse their own casting: two cards.
  - A dropped connection without a reload: if the acting GM loads during the gap, it lapses that player's casting, though the player's browser still holds it. Complete still works for the player, but its card says lapsed.
  - Phase 1 and a critical injury now wait up to 10 seconds for a holder that never acknowledges, and up to five minutes for one that has (its step's dialog), before going on as before.
  - **Power Crystal settlements are queued per client.** A GM's drain and a player's spend landing at the same moment on two clients are not queued against each other, so the crystal can be under-drawn. Left as it is (the second review's note 8).
  - **A settlement whose write never returns** holds that creature's later settlements on that client for at most 10 seconds, then the queue moves on with a console warning (the second review). The settlement that went ahead read the crystal as it last landed.
- **The startup sweep reads world actors only,** as it did before. A casting on an unlinked token's actor is not swept.
- **The whole-core scan for the broad `isGM` guard** checked every `create*`, `update*`, `delete*`, `pre*`, world-time, combat and `ready` hook in `module/` and `scripts/`, and the functions they delegate to. It found no world-changing hook guarded by `isGM` beyond the first five. The remaining `isGM` checks are on buttons, dialogs and macros the GM invokes, migration (which also asks for the active GM), encumbrance (which also asks `isActingGM`), and the target relay's error reply. The three unguarded hooks it noted are fixed above.
